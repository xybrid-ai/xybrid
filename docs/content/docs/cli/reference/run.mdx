title: xybrid run

Execute a hybrid pipeline on the current device.

## Usage

```bash
xybrid run --config <path>
xybrid run --pipeline <name>
xybrid run --pipeline <name> --dry-run
xybrid run --directory <dir> --input-text <context> --choice <id>=<text>
xybrid run --model-file <gguf> --decision <request.json>
```

## Options

| Option | Short | Description |
|--------|-------|-------------|
| `--config` | `-c` | Load a pipeline YAML file directly |
| `--pipeline` | `-p` | Look up `<name>.yml` under `examples/` |
| `--bundle` | `-b` | Run a `.xyb` bundle file directly |
| `--input-text` | | Text input for text-based models (LLM, TTS) |
| `--input-audio` | | Path to an audio file for audio-based models (ASR) — WAV, MP3, OGG, or FLAC |
| `--choice` | | A candidate for a choice-scoring model, as `ID=TEXT`; repeatable. See [Choice scoring](#choice-scoring) |
| `--decision` | | A decision request in SystemOne JSON, from a file or `-` for stdin. See [Decision requests](#decision-requests) |
| `--output` | `-o` | Save the result: audio as `.wav`, text as `.txt`, choice scores and decision responses as JSON |
| `--target` | | Force model format (`onnx`, `coreml`, `tflite`); auto-detected if omitted |
| `--dry-run` | | Simulate routing without execution |
| `--policy` | | Load a policy bundle (YAML/JSON) that constrains routing — see [Hybrid Execution › Policies](/docs/concepts/hybrid-execution#policies) |
| `--trace` | | Enable execution tracing with flame graph + LLM metrics output |
| `--trace-export` | | Export the trace to a JSON file (Chrome trace format) |

## Behavior

1. Parses YAML into `PipelineConfig`
2. Runs policy → routing → execution loop
3. Prints stage latency and routing summaries

In dry-run mode the CLI decides the first stage (policy and route) exactly as a real run would, at the current device snapshot, without running inference. Later stages are reported as unknown: their input is the previous stage's output, which does not exist without execution.

## Examples

### Run from config file

```bash
xybrid run --config ./pipelines/voice-assistant.yaml
```

### Run named pipeline

```bash
xybrid run --pipeline hiiipe
```

Looks for `hiiipe.yml` or `hiiipe.yaml` in:
- `xybrid-cli/examples/`
- `./examples/`

### Dry run (simulate only)

```bash
xybrid run --pipeline hiiipe --dry-run
```

Output shows the first-stage decision without running inference:

```
  Stage 1 llm
  Declared         target: auto
  Provider         openai
  Policy           ALLOWED
  Reason           all policy checks passed
  Routing          local (default_local)

  Stage 2 tts
  Policy           UNKNOWN
  Routing          UNKNOWN
  Output           upstream output unavailable without execution
```

### With a policy and Xybrid Platform

The primary hybrid example keeps the local model on the device and uses
Xybrid Platform for cloud inference. Only the Xybrid API key belongs on the
device; the upstream provider credentials are configured on the platform.

```bash
XYBRID_API_KEY="<your-xybrid-api-key>" xybrid run \
  -c crates/xybrid-cli/examples/hybrid-platform.yaml \
  --policy crates/xybrid-cli/examples/policies/prefer-cloud.yaml \
  --input-text "Summarise the plot of Dune in two sentences." -v
```

Swap in `policies/local-only.yaml` to keep the same prompt on the device, or
`policies/privacy.yaml` to route by content. `-v` also prints the raw
`routing_decision` JSON line.

Use `--platform-url <base-url>` for a staging or self-hosted platform. The
example uses `gpt-4o-mini`, which the platform must have configured upstream.

### Direct provider testing

`crates/xybrid-cli/examples/hybrid-deepseek.yaml` uses `backend: direct` and
`DEEPSEEK_API_KEY` for direct DeepSeek calls. Keep it for manual provider checks;
automated policy-routing tests use a loopback fake DeepSeek endpoint with dummy
credentials.

## Choice scoring

A choice-scoring model (a `ChoiceScorer` in its `model_metadata.json`) reads one
context and a closed list of candidates and returns one score per candidate,
without generating text. Pass the context with `--input-text` and each
candidate with `--choice ID=TEXT`. The id names the candidate in the result and
the model reads the text; the text is everything after the first `=` and may
be empty. The model scores its own fixed choices after yours, so a scorer with
at least two of them, like CUA-S1-FORMS, also runs without `--choice`.

CUA-S1-FORMS scores form actions against a page. From a checkout, stage it with
`./integration-tests/download.sh cua-s1-forms` (it regenerates the ONNX export
from the pinned checkpoint), then:

```bash
xybrid run --directory integration-tests/fixtures/models/cua-s1-forms \
  --input-text 'TASK fill the form from the document, then submit
FORM Intake
ELEMENT Edit "Phone" value=""' \
  --choice tel="fill Tel: (503) 555-0142" --choice name="fill Name: Jane Doe" \
  --output scores.json
```

```
  ID     Score   Logit
  ────────────────────────────────
  tel    0.9997   29.9987  best
  name   0.0000    3.8055
  check  0.0000   -1.2357  fixed
  click  0.0000  -13.4527  fixed
  skip   0.0003   21.8863  fixed

  Margin           0.9994
  › Scores rank these candidates against each other; they are not calibrated probabilities
```

The rows come in the order offered: your choices, then the model's fixed
choices (`check`, `click` and `skip` for FORMS). `Score` is the softmax of the
logits over these candidates, `Logit` the model's raw output, and `Margin` the
best score's lead over the runner-up. The highest score is marked `best`: equal
scores go to the higher logit, and an exact tie to the first candidate. A score
says how the model ranks the offered candidates, not how likely one is to be
right, and acting on it is up to the caller. `--output` saves the scores at
full precision, without the rounding:

```json
{
  "entries": [
    { "id": "tel", "logit": 29.99869, "score": 0.9997003, "fixed": false },
    { "id": "name", "logit": 3.80547, "score": 4.2101643e-12, "fixed": false },
    { "id": "check", "logit": -1.2357253, "score": 2.7222987e-14, "fixed": true },
    { "id": "click", "logit": -13.452731, "score": 1.3463486e-19, "fixed": true },
    { "id": "skip", "logit": 21.886269, "score": 0.00029970234, "fixed": true }
  ],
  "label_mass": null
}
```

FORMS reads the first 224 bytes of the context and the first 96 bytes of each
candidate, and cuts longer input without saying so.

A request is checked before the model runs, and by `--dry-run` too. It is
refused when the context is empty, when an id is empty, repeated or one of the
model's fixed ids, and when there are fewer than two candidates or more than the
model accepts (64 for FORMS), fixed ones included. These refusals count
positions from 0: a candidate in the order offered, a caller choice among your
`--choice` flags and a fixed choice among the model's fixed choices. They never
quote your ids or texts. A `--choice` with no `=`, or nothing before it, is a
usage error, which repeats the argument like any other. A model that is not a
choice scorer refuses `--choice`.

`--choice` needs `--input-text`, and cannot be combined with `--config`,
`--pipeline`, `--input-audio`, `--input-image`, `--voice`, `--max-tokens` or
`--speculative-cloud`. A choice scorer refuses `--input-audio`,
`--input-image`, `--voice` and `--max-tokens` without `--choice` too.
`xybrid repl` refuses a choice scorer, also as a pipeline stage, and so does
`--speculative-cloud`, also with `--dry-run`.

## Decision requests

A decision model reads a state (text, JSON, or nothing) and answers typed
questions about it: pick an option, yes or no, or a level on a scale. It reads
each answer from the model without generating text. `--decision` takes such a
request in the JSON shape that llama.cpp's server answers at `/v1/systemone`
(SystemOne, subset v1: the text profile of LiquidAI's LFM3 d1), from a file or
from stdin with `-`. It needs a model (`--model-file`, `--model`,
`--directory`, `--huggingface` or `--bundle`), and takes `--target`,
`--dry-run` and `--output` besides. It cannot be combined with `--config`,
`--pipeline`, `--policy`, `--input-text`, `--input-audio`, `--input-image`,
`--choice`, `--voice`, `--max-tokens`, `--show-reasoning`,
`--speculative-cloud`, `--trace` or `--trace-export`: the request holds the
input, and none of the others applies to a decision run.

<Callout type="warn">
This build checks decision requests but cannot run them yet. A valid request
ends with `decision models are not supported by this build yet`, before any
model is opened. `--dry-run` checks the request alone and succeeds when it is
valid; the model is not checked. Neither writes `--output`.
</Callout>

```bash
xybrid run --model-file d1-2B-Q4_K_M.gguf --decision request.json --output response.json
cat request.json | xybrid run --model-file d1-2B-Q4_K_M.gguf --decision - --dry-run
```

### Request

```json
{
  "state": "I was charged twice this month, please refund one of them.",
  "questions": {
    "refund": {"type": "noul", "instructions": "Is the customer asking for a refund?"},
    "team": {
      "type": "choice",
      "instructions": "Which team should handle this?",
      "criteria": {"billing": "Charges, refunds, invoices", "technical": "App or site faults", "fraud": "Suspected unauthorised use"}
    },
    "urgency": {
      "type": "score",
      "instructions": "How urgent is this?",
      "criteria": ["Can wait", "Today", "Blocking the customer now"]
    }
  }
}
```

- `state` is required: text, JSON, or `null` for no state (`""` is an empty
  state, not a missing one).
- `questions` is a non-empty object of question id to question; the answers
  come back in its order.
- `type` is `choice` (pick one option), `noul` (yes or no) or `score` (a level).
- `instructions` are required: text or JSON.
- `criteria`: a choice takes an object of option key to description, in order
  (1 to 255 options); a score takes an array of 2 to 10 level descriptions,
  lowest first; a noul may describe `"true"`, `"false"` or both, or have no
  criteria. A description is text, JSON, or `null` for none. An option key can
  change the answer: LFM3 d1 shows the model single-letter keys as labels, and
  the key itself (`_` read as a space) in place of a missing or empty
  description.
- `model` is accepted and ignored.

Text reaches the model as written. In JSON, member order and integer/float
identity are preserved (`1` and `1.0` differ), while JSON whitespace and the
spelling of numbers are normalized (`1E2` is read as the float `100.0`, `2.50`
as `2.5`).

### Refusals

A request is refused before any model is opened, and by `--dry-run` too. The
error names its kind and positions (counting from 0), never the request's
content:

| Kind | When |
|------|------|
| `invalid_json` | The request is not one JSON value |
| `invalid_request` | It is JSON, but not an object |
| `duplicate_key` | An object repeats a key, anywhere in the request |
| `missing_state` | No `state` |
| `invalid_questions` | `questions` missing, not an object, or empty |
| `invalid_question` | A question that is not an object |
| `missing_instructions` | `instructions` missing or `null` |
| `spoken_instructions` | Instructions that are an `input_audio` part |
| `invalid_question_type` | `type` missing, not a string, or not one of the three |
| `invalid_criteria` | Criteria of the wrong shape for the type |
| `level_count` | A score with fewer than 2 or more than 10 levels |
| `too_many_options` | A choice with more than 255 options |
| `media_unsupported` | A `files`, `images` or `videos` field (even empty or `null`), or an image, audio or video part in the state's chat messages |
| `unknown_field` | Any other field at the top level, in a question (`multiple`, say) or in noul criteria (`yes` and `no` included) |
| `empty_question_id`, `empty_option_key` | An id or option key that is the empty string |
| `json_too_deep` | JSON content (state, instructions, a description) nested more than 128 levels deep |
| `number_out_of_range` | A number beyond the 64-bit float range (`1e400`), or an integer from 9223372036854775808 to 18446744073709551615, which the model would read wrapped to a negative number (larger integers are read as floats, as llama.cpp reads them) |
| `request_too_large` | A request larger than 8 MiB, with more than 131,072 JSON values, or with more than 65,536 in one piece of content |

llama.cpp's server ignores unknown fields and keeps the last of repeated keys;
`xybrid` refuses both, so nothing in a request is silently dropped. A request
that asks more than 16 questions is refused too. LFM3 d1 has lower limits of
its own (nesting, a token budget per question), checked when it prepares the
request.

### Response

Once a build runs decision models, the response is printed, and saved by
`--output`. It follows llama.cpp's, member by member:

```json
{
  "model": "d1-2B-Q4_K_M.gguf",
  "answers": {
    "refund": {
      "type": "noul",
      "noul": 0.9973703517289787
    },
    "team": {
      "type": "choice",
      "choice": "billing",
      "probabilities": {
        "billing": 0.9653423092419502,
        "technical": 0.016056498667205623,
        "fraud": 0.018601192090844064
      },
      "confidence": 0.9653423092419502
    },
    "urgency": {
      "type": "score",
      "score": 0.0,
      "legend": {
        "0": "Can wait",
        "1": "Today",
        "2": "Blocking the customer now"
      },
      "probabilities": {
        "0": 0.7813993464828815,
        "1": 0.19769099249323435,
        "2": 0.02090966102388407
      },
      "confidence": 0.7813993464828815
    }
  },
  "usage": {
    "input_tokens": 160,
    "output_tokens": 0
  }
}
```

These are llama.cpp's own answers to the request above on d1-2B (Q4_K_M, CPU);
other builds and settings move the last digits.

- `noul` is the probability of yes; `choice` the most probable option (the
  first on a tie); `score` LFM3 d1's median level, the first whose cumulative
  probability reaches one half.
- `probabilities` come in option or level order; `legend` gives each level's
  description back as the request had it (`null` for none), with the same
  member order and integer/float identity, and normalized whitespace and
  number spelling.
- `confidence` is LFM3 d1's highest probability.
- The probabilities follow the temperature the model's publisher set: they
  rank the answers the model weighed, and are not calibrated chances of being
  right.
- `input_tokens` counts the tokens of every model pass (one per question for
  LFM3 d1).
- Every computed number is a 64-bit float written with the fewest digits that
  read back as the same value, so a correctly rounded JSON parser gets it back
  exactly.

## Pipeline Format

The `run` command expects YAML pipelines:

```yaml
name: "voice-assistant"
stages:
  - whisper-tiny@1.0
  - target: integration
    provider: openai
    model: gpt-4o-mini
  - kokoro-82m@0.1
```

## Tracing LLM Inference

When `--trace` is passed and the pipeline includes an LLM stage, the CLI
prints an additional metrics block after the output:

```
📊 LLM Trace:
------------------------------------------------------------
  TTFT                  : 412 ms
  Decode TPS            : 42.80 tok/s
  Prefill TPS           : 184.20 tok/s
  Wallclock TPS         : 38.10 tok/s
  Mean ITL              : 14.30 ms
  p95 ITL               : 28 ms
  Emitted chunks        : 64
  Tokens generated      : 64
  Finish reason         : stop
------------------------------------------------------------
```

These values are read from the output envelope's metadata, populated by
the LLM adapter's streaming path. Non-LLM stages (ASR, TTS, embedding)
do not emit these fields and the block is skipped.
